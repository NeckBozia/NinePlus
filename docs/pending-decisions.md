## D1 · 磁贴刷新的范围

**规格现在的写法**：磁贴执行指令后只拉取当前那辆车的状态（`GET /vehicles/{sn}/dashboard`）。

**iOS 的行为**：拉全量（`GET /vehicles` 加上每辆车各一次 dashboard）。两辆车就是 3 个串行请求。

**分歧点**：Widget 扩展的网络预算只有 12 秒（`NinebotWidgetControlIntents.swift:80-86` 把超时压到 8/12 秒），全量刷新在慢网下容易超时失败。但只刷一辆的代价是其他车的缓存数据变旧。

**决定时机**：Phase 1 的 1.3。

**要问的**：你有几辆车？只有一辆的话这条根本无所谓，直接按只刷一辆。

## D2 · 指令成功但刷新失败时怎么提示

**规格现在的写法**：分两条提示 —— 「上电指令已发送」+「车况刷新失败，下拉重试」。

**iOS 的行为**：指令成功后先把状态设成成功，紧接着刷新失败会把它抹掉并报错。结果是**车已经开锁了，界面显示报错**（`NinebotViewModel.swift:395` 与 `:663-667`）。

**分歧点**：iOS 那个行为是明确的缺陷，会让人以为指令没生效而重复操作。但改掉之后两端提示不一致。

**决定时机**：Phase 1 的 1.2。

**要问的**：iOS 侧要不要一起修？一起修就没有不一致问题了。

## D9 · 服务端充满时刻用「现在」而不是「快照时间」比对 〔你看过了，先不动〕

**发现于**：领域层抽取时给充电状态补测试。

**一句话**：算「还要充多久」时减错了基准时间，结果一份放久了的缓存会在半电量时显示「已充满」。

**举个具体例子**：

1. 14:00 你打开 App。服务端说「这辆车预计 14:30 充满」。App 把整份车况存进缓存。
2. 15:00 你再打开 App。冷启动先显示缓存，也就是那句「预计 14:30 充满」。
3. App 要算「还剩多少分钟」，它的做法是 **14:30 减去现在（15:00）** = 负 30 分钟 → 夹到 0 → 显示「已充满」。
4. 实际电量可能才 50%。

正确的做法是 **14:30 减去这份数据是什么时候拿到的（14:00）** = 还剩 30 分钟。

代码位置：`serverRemainingChargeMinutes` 用了 `timeIntervalSinceNow`，而不是和这份快照的 `updatedAt` 相减。

**已用测试钉住现状**（`ChargingStatusTests.testStaleServerTimestampReadsAsFullyCharged`），没有改行为。

三个选项：

| 方案 | 效果 |
| --- | --- |
| 不动 | 两端一致地保留这个怪行为 |
| 改成和 `updatedAt` 比对 | 缓存快照的剩余时间保持它当时的语义，更符合直觉 |
| 快照过期就不显示服务端时刻 | 回退到本地公式估算 |

注意社区服务端**不返回预测**，所以这条现在根本触发不到。等将来换成带预测的服务端才有影响。

**当前处置（你定的）**：先记下来，两端都不动。等换成会返回预测的服务端时再回来定。

**决定时机**：换服务端时。

## D11 · 时长显示在临界点上会跳到「下一档」的数字 〔已定：改，已改完〕

**发现于**：领域层抽取时给记录周期和时长格式化补测试。

**一句话**：挑单位用的是精确值，显示的数字却四舍五入了，所以刚好卡在临界点时两者对不上。

**举个具体例子** —— 「记录周期」这一栏的规则是：不满 1 小时显示分钟，1 小时到 1 天显示小时，超过 1 天显示天。

- 跨度 59 分 59 秒（3599 秒）：精确值不满 1 小时 → 走**分钟**档；但 59.98 分钟四舍五入成整数是 60 → 屏幕上是 **「60 分钟」**，而不是「1 小时」。
- 跨度 23 小时 59 分 59 秒：同理显示 **「24 小时」**，而不是「1 天」。

`formatDuration`（`Shared/NinebotFormatting.swift`）也是同一个毛病。

**影响**：不影响任何计算，纯粹是看着怪，而且只在临界的那一秒出现。

**结论（你定的）**：改。挑档改成用**取整后的值**比，iOS 侧已经改完，Android 照改后的行为实现。

改法是加一个 `displayRounded(_:maximumFractionDigits:)`（`Shared/NinebotFormatting.swift`），把「该显示成几」先算出来，再拿它去比边界。三处都改了：

**后续（L10，你又定了一条）**：四处的显示精度**统一成一位小数**，「精确那种」。原先 `formatDuration` 的分钟不带小数，导致同一个输入 59.9 分钟在骑行时长那里显示「1 小时」、在充电剩余时间那里显示「59.9 分钟」。现在四处口径完全一致：

| 位置 | 分钟显示精度 | 翻档点 | 59.9 分钟显示成 |
| --- | --- | --- | --- |
| 记录周期，分钟→小时（`NinebotHistoryPeriod`） | 1 位小数 | 59.95 分钟 | 59.9 分钟 |
| 骑行时长（`formatDuration`） | 1 位小数 | 59.95 分钟 | 59.9 分钟 |
| 充电剩余时间（`durationText`） | 1 位小数 | 59.95 分钟 | 59.9 分钟 |
| 记录周期，小时→天 | 小时 1 位小数 | 23.95 小时 | —— |

整数不带多余的小数位（`45` 显示成「45 分钟」不是「45.0 分钟」），因为 `minimumFractionDigits` 是 0。翻档之后显示的还是真实跨度，不会拍平成整数 —— 23:55 显示「23.9 小时」而不是「1 天」。

精度常量：`durationFractionDigits`（`Shared/NinebotFormatting.swift`），`NinebotHistoryPeriod` 的两个精度常量都指向它，改一处就三处同步。

测试：`HistoryPeriodTests.testJustUnderABoundaryRollsUp`、`FormattingTests.testDurationKeepsItsDecimalAndRollsUpAt5995`、`ChargingStatusTests.testRemainingTimeRollsUpAtOneDecimal`。

## D12 · 服务端用社区适配器还是 `ninecli serve` 〔已定：社区适配器 —— 要给朋友用〕

**发现于**：回答「为什么不能连九号官方接口」时查 `nine-proxy` 分支。

**背景**：客户端历史上有两种模式，对应两种服务端。

| | 平台模式（`main` 只剩这个） | 代理模式（只在 `nine-proxy` 分支） |
| --- | --- | --- |
| 登录端点 | `POST /accounts/login` | `POST /auth/login`、`/auth/refresh` |
| 服务端 | NinePlus Platform（拿不到）或**社区适配器** | **`ninecli serve`** |
| 默认端口 | 19009 | 127.0.0.1:18009 |
| 特点 | 多账号、管理后台、可以自己改 | 单账号、ninecli 自带、官方描述「把加密的九号 API 暴露成明文 REST」 |

**结论**：用**社区适配器**（平台模式），fork 自己改。

**定这条的理由是新加的约束：要同时给两位朋友用，一共三个账号。**

`ninecli serve` 是**单账号**的 —— `nine-proxy` 分支的设置页原话是「会直接登录当前 `ninecli serve`，**会替换代理上的单账号会话**」，一个实例服务不了两个人。三个人就要三个实例三个端口，而它的 bearer token 是全局一个、不按人分，等于没有按人鉴权。

社区适配器的多账号是一等功能，而且实现得不错（逐行看过 `server.py`）：

| 项 | 实现 |
| --- | --- |
| NineBot+ 密码 | PBKDF2-HMAC-SHA256，210,000 次迭代，16 字节随机盐（`_password_hash`） |
| 九号密码 | **只用于首次换取令牌，不落盘**（`client_settings` 之后传空字符串），管理页也明确写了这句 |
| 账号隔离 | 每个账号一个独立的 ninecli 令牌目录 `<base>/accounts/<sha256(账号)[:24]>` |
| 新增账号时 | 先真的调一次 `vehicles()` 验证九号登录，通过了才写盘 |

所以 `ninecli serve` 那条路只在**单人自用**时才值得考虑。下面的分析留着，将来若变成单人再翻出来。

**给朋友用是后置目标**（你定的）：先把自己这边做得差不多，再考虑上人。所以下面这些不按「三人并发」排优先级：

| | 什么时候管 |
| --- | --- |
| 请求缓存、会话落盘 | **已写好补丁**，见 `server-patches/`。单人也受益（缓存解掉 Widget 12 秒预算的风险，会话落盘免掉重启后重新绑定），所以先做了 |
| `travel-sync` 空桩、`/healthz` 假阳性 | 排在后面 |
| 管理后台别暴露公网、告知朋友信任链 | 真要上人之前再过一遍 |

**两种模式的端点差异（逐条比对两个分支的客户端得出）**：车辆相关的端点**完全相同**，只有登录不一样。

| 只有平台模式有 | 在社区适配器上的实际状态 |
| --- | --- |
| `GET /vehicles/{sn}/dashboard` | 适配器自己拼的聚合响应（内部照样打 6+ 次 ninecli）。代理模式下客户端用 `status` + `battery` 自己拼 —— 而 iOS 在社区适配器上**本来就走这条兜底分支**（响应里没有 `state` 键） |
| `GET /vehicles/{sn}/prediction` | 空桩，恒返回 `{}` |
| `POST /vehicles/{sn}/prediction-settings` | 空桩，回显请求体 |
| `POST /live-activities/register` | 兼容桩，适配器不发 APNs；而且已定不做推送 |

| 只有代理模式有 | 说明 |
| --- | --- |
| `POST /auth/login`、`/auth/refresh` | 代理模式的登录与续期 |
| `/auth/login-code`、`/accounts/login-code`（含 `/consume`） | 短信验证码登录，`main` 分支把这套砍了 |

**结论就在这张表里**：那四个「只有平台模式有」的端点，在社区适配器上**没有一个是真的** —— 一个是它自己拼的，两个空桩，一个已定不做。所以走 `ninecli serve` 在功能上几乎不损失。

**分歧点**：`ninecli serve` 少一层，而且它自己常驻，没有「每个请求 fork 一个 8.9 MB Go 进程」那套开销 —— 这正好是社区适配器最大的性能问题。也不需要维护 fork。

代价：
1. **没验证过 `ninecli serve` 的真实路由表**。我是从 `nine-proxy` 分支客户端发出的请求反推的（客户端就是照它写的，推断很强但不是实测）。`travel` 那三条在它上面通不通，尤其要试
2. 默认只监听 `127.0.0.1:18009`，手机要连得改成 `0.0.0.0` 或者前面挂反向代理
3. 没有多账号、没有管理后台
4. 闭源二进制，出问题只能绕不能修 —— 社区适配器是 Python，能改
5. Android 要实现代理模式的登录流程（`/auth/login` + `/auth/refresh`），参考实现在 `origin/nine-proxy` 的 `NinebotProxyClient.swift`

**要做的验证**：跑起来，先打 `/auth/login`，再逐个打车辆端点（`vehicles`、`status`、`battery`、`travel`、`travel/{id}`、四个控制指令）。约半小时。

**还有第三个选项**：两个都用 —— `ninecli serve` 打底，社区适配器只在它确实缺东西时补。不过多一层部署，除非验证发现它缺得厉害，否则没必要。

**决定时机**：Phase 0 开工前，和 V1–V10 那批实测一起做。它决定 Android 侧对齐哪一套端点。

编号按区域分前缀，互不冲突：**T** 行程 · **P** 传感器 · **R** 轨迹 · **W** Widget · **C** 充电岛 · **S** 系统集成 · **I** 图标 · **A** 服务端 API · **L** 文案。上面 D1–D12 是跨阶段的通用决策。

### 先说清一件事：V1–V10 不是决策

那 10 条是**实测项** —— 需要有人把社区服务端跑起来，照着 `community-server-api-check.md` 第四节的命令跑一遍。它们不用你拍板，但**跑完才能定好几条决策**（A1、R14、A5、A7 都卡在这里）。整套跑完大约半天。
